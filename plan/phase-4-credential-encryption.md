# Phase 4 — credential encryption and real API keys

**Status:** not started
**Depends on:** Phase 3c
**Breadcrumbs in the tree:** `scripts/generate-secrets.mjs:17`,
`backend/src/config/env.ts:116-117, 142-148`,
`backend/test/env.spec.ts:131`, `backend/src/common/logging/redaction.ts:29`

## The problem this phase exists to solve

The configuration for this phase is **fully built and completely unused.**

- `CREDENTIALS_MASTER_KEY` is generated by `scripts/generate-secrets.mjs:19`
  (32 bytes hex, so it decodes to exactly 32 bytes for AES-256).
- It is documented in `backend/.env.example`.
- It is on the redaction list (`redaction.ts:29`).
- It is covered by tests: `env.spec.ts:131` pins the empty-is-absent behaviour.
- **And it is hard-required at boot in production** (`env.ts:142-148`), with an
  error message that says "Phase 4 encrypts connector credentials with it".

Meanwhile there is **no crypto code in the repository at all.** No
`createCipheriv`, no `Connector` model, no `ApiKey` model, no
`src/integrations/`. The key protects nothing.

So production today demands an operator generate and manage a secret that has
no consumer, while the frontend's `ApiKeys.tsx` renders a convincing API key
table backed by **hardcoded values and a `Math.random`-style hex generator**,
with no backend call anywhere in the file.

This phase makes the key load-bearing.

## Scope

Backend crypto + real API keys. **Not** live connector OAuth — see "out of
scope" below.

### 4-1 — the crypto service

`backend/src/common/crypto/` (or `src/crypto/` — follow whatever the repo's
module layout settles on):

- AES-256-GCM `encrypt` / `decrypt` using Node's `crypto` only. No new
  dependency.
- Per-record random IV. Never reuse an IV with the same key.
- Auth tag verified on decrypt; a tampered ciphertext **must throw**, never
  return garbage.
- **Versioned ciphertext format**, so the scheme can change later without a
  migration. Something like `v1:<keyId>:<iv>:<tag>:<ciphertext>`, base64url
  throughout.
- **Key rotation.** Multiple keys can be valid at once; the key id in the
  envelope selects which to decrypt with. Rotation is then a background
  re-encrypt, and a row encrypted under a retired key is still readable until
  it is rewritten.
- Fail **loudly and specifically** on a wrong key or a malformed envelope. A
  silent `undefined` from a decrypt is how credential bugs become
  unauthenticated access.

Add a redaction entry for any new field name, in the same style as
`redaction.ts`.

### 4-2 — the `ApiKey` model

A migration. Design:

- The key is **hashed at rest**, never stored. Same posture as
  `Session.tokenHash` (`schema.prisma:260-262`).
- A short `prefix` (e.g. `rw_live_a1b2c3`) stored in plaintext and indexed, so
  the key can be **looked up** by prefix and the rest verified with a constant-
  time compare. Without the prefix there is no way to find the row.
- `scopes` — reuse the existing permission vocabulary rather than inventing a
  parallel one.
- `lastUsedAt`, `revokedAt`, `expiresAt`, `name`.
- `companyId` for tenant scoping, indexed. Every query filters by it.

**The key is returned exactly once**, at creation, and never again. That is the
whole point of hashing it, and the UI has to say so plainly rather than showing
a masked value that implies it can be recovered.

### 4-3 — real endpoints behind the existing UI

CRUD + verification, tenant-scoped, permission-gated. Decide and write down
which role may issue and revoke keys — a key is a bearer credential for the
whole tenant, so this is at least `ADMIN` and arguably `OWNER` only. Do not
default to `metrics:write` because it is convenient.

Then replace the body of `frontend/src/pages/ApiKeys.tsx`, which currently
imports no `api` at all. Keep its layout; replace `seedKeys` and `makeMasked`
with real calls.

### 4-4 — key verification on use

If API keys are actually accepted anywhere, there must be a guard that verifies
them. Decide in this phase whether that is in scope; if it is not, the phase
doc should say the keys are stored but not yet accepted, so the next reader
does not assume they are live.

## Out of scope, deliberately

**Live Stripe/bank OAuth and encrypted connector token storage.** The README
already names these v1.1+/v2 scope (`README.md:209-213`), and adding a real
financial integration is a project of its own. `Connectors` stay read-only
placeholders; `Integrations.tsx` and `Billing.tsx` keep their honest
"coming soon" labels rather than gaining fake affordances.

`ApiKeys.tsx` being fully simulated is the exception — it is a plausible-looking
screen backed by nothing, which is worse than an honest placeholder. That is why
it is in scope.

## Tests

- Crypto: envelope round-trip, tamper detection on each of IV/tag/ciphertext,
  wrong key throws, version dispatch, key rotation (encrypt under old, decrypt
  after old is retired, re-encrypt, decrypt under new).
- Keys: create returns the plaintext once and stores only a hash, prefix lookup
  works, revoked keys fail, expiry enforced, cross-tenant access is impossible.
- `test/db/` for everything that touches persisted state or tenant scoping.
- `env.spec.ts` already covers the empty-vs-absent and short-key cases; leave
  them passing.
- A test asserting **no plaintext key ever reaches the database** is worth more
  than the individual round-trip tests.
